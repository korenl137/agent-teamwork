# Model selection

The caller selects models through the host's supported session, definition or per-call
settings. Respect user/organization policy, availability and authorized cost limits.
This reference defines selection principles, not a model router or provider preset.
Public role definitions omit model fields so consumer choices can apply.

## Match capability to the work

| Work | Selection principle |
|---|---|
| Conducting collaboration | Use enough reasoning capacity for requirements, decomposition, dependency decisions and integration; mistakes here can affect many workers |
| Bounded implementation | Start with a model capable of the specified task and verification; escalate for design judgment, broad dependencies or failure with new evidence |
| Research | Distinguish collecting sources from comparing and synthesizing them; use capacity appropriate to the reasoning required |
| Independent review | Scale judgment to change complexity, impact and uncertainty; a reviewer need not be weaker than the conductor or implementer |
| State inspection | Match cross-artifact reconciliation complexity; a stronger model cannot replace missing evidence or unavailable tools |

Do not choose every worker's model solely from the conductor's choice. Do not weaken
review merely because implementation was mechanical. Reconsider the choice when scope,
risk or observed difficulty changes. A capable conductor may still do small direct work;
model strength does not remove the independent-review or approval boundary.

## Availability and evidence

If a required model is unavailable, report the gap and follow the consumer's fallback
policy. Do not silently substitute a weaker model. If the policy does not authorize an
alternative, resolve that choice before the dependent action; continue independent work.
An opaque native review route does not prove a required model was used. Use a supported
explicit-selection route when policy requires one, or report that the requirement is
unverified rather than claiming success.

Record the requested and observed model when available, the relevant role/scope, and
any substitution or unknown value in the existing task report. Do not infer the actual
model solely from a definition or alias. Attribute cost/usage to the account or profile
observed and label unavailable data unknown. Do not add benchmark runs, numeric routing
thresholds or permanent monitoring without a concrete task and authorization.
